# 問い合わせ保持・削除ポリシー（Issue #98）

## 1. 決定事項と現行実装

2026-10-20、サイト運用者は **問い合わせ本文・連絡先365日、添付ファイル本体90日** を維持する方針を承認した。
双方を同じ保存期間には統一しない。個人情報の削除を安全に実行するための実装・運用承認は**まだ完了していない**。

| データ | 決定した期間 | 起算点・実装状況 |
| --- | --- | --- |
| 問い合わせ本文・氏名・メール・内部メモ | 最後のやり取りから365日を目安 | 現コードは`updatedAt`基準で、メモ/状態更新でも延長。正しい対話日時との一致は未保証 |
| 添付の実体（S3 `clean/`） | 90日 | S3 Lifecycleはcleanオブジェクト生成日から90日。フォーム受付日時とは異なる場合がある |
| スキャン中のS3 `quarantine/` | 1日 | Lifecycleで自動期限切れ |
| 添付のDB参照（ファイル名・キー・ハッシュ等） | DB問い合わせと同じ | バイナリがS3から消えてもメタデータは残り得る |
| DB/S3のバックアップ、ログ、復旧点 | 別途確認 | 本表の日数はバックアップの完全消去を保証しない |

既存プライバシーポリシーの「最後のやり取りから1年を目安」「受付から90日」と、技術上の`updatedAt`・S3 clean作成日の差は**未解決**。
公開文面の正確性を確認した上で、別PRで起算点の変更や補足を検討する。
S3 Lifecycleの削除は非同期処理であり、90日到達時刻に即座に消える保証はない。

## 2. ライフサイクルと正常時の利用者体験

1. 問い合わせが受理される。添付は検査後に`clean/`へコピーされ、DBにS3参照が記録される。
2. 添付のcleanオブジェクト作成後90日を過ぎると、S3 Lifecycleが削除する。本文は原則残す。
3. 添付を管理者が開く際は認証・Payloadアクセス検査後にS3存在確認を行う。対象がない場合はHTTP404、S3障害時は503、存在時のみ短期署名URLに302する（PR #145）。
4. 本文の365日経過候補は、週次`Ops Health`の**dry-runだけ**で報告する（PR #144）。削除は自動実行しない。
5. 削除と監査/復元の仕組みの検証・承認が完了するまで、`RETENTION_PURGE_ENABLED`や`RETENTION_APPLY`を設定しない。

現行APIには**直接リクエスト`apply: true`と環境側`RETENTION_PURGE_ENABLED=true`の両方で削除を行える経路**が残っている。
GitHubの週次ジョブがdry-run専用であることと、APIが完全に削除不能であることを混同しない。

## 3. 例外と未解決点

- `status: new`（未対応）は現行のDB保持削除対象から除外され、365日を超えて残り得る。週次dry-runで`updatedAt`基準の期限超過New件数を集計するが、最後の対話日による厳密な年齢判定や、例外理由/対応責任者/再評価期限と通知は未実装。未対応を無期限保有してよいと判断したわけではない。
- `updatedAt`は管理者メモ・ステータス変更等でも変わる。厳密に「最後のやり取り」にする場合、`lastInteractionAt`などの別項目、移行/backfill、既存データとの互換性の検証が必要。
- 法令に基づく保存、紛争解決、削除請求の扱いはそれぞれ承認/記録し、通常の90日・365日と区別する。
- 90日を過ぎてもS3が非同期削除中の場合、推定日時だけで「削除済み」と表示しない。CMSの有無判定・HTTP応答を優先する。
- 本人削除請求、重複オブジェクト、バックアップに残った個人情報は通常Lifecycleと別の対応が必要。

## 4. DB/S3削除整合の推奨実装

**現段階では設計のみ。** DB削除は既存`POST /api/ops/retention`で`payload.delete`するだけで、S3オブジェクトとの原子的な削除ではない。

- 事前照合: 削除要求の権限・保有例外・参照するオブジェクトキーの帰属を検証し、状態を保護されたDBのアウトボックスに記録する。個人情報/S3キーを公開ログ・Issueに含めない。
- S3削除: 対象の`clean/`だけを処理し、成功または既に存在しない404を冪等な完了とする。403/5xx/タイムアウトは**削除完了とみなさず**、再試行可能な状態とする。
- DB処理: S3の完了条件と照合してから本文の削除・削除完了の監査を確定する。処理途中に失敗しても、アウトボックスの状態から再開できること。
- 再試行: 重複イベント/並列ジョブ/タイムアウト/部分成功でも二重削除や他人のオブジェクト削除を起こさない。指数バックオフ、試行上限、dead-letterと管理者アラートを検討する。
- 孤立ファイル: S3一覧とDB参照を読み取り照合し、フォーム送信待ち（添付トークン有効期間）やスキャン中の猶予を考慮する。**不一致を検知しただけで自動削除はしない。**
- 保存期間変更はしない。AWSリソースはTerraform stateで管理していない可能性があるため、現行設定を未確認のままterraform applyしない。

アウトボックスのスキーマ・トランザクション境界・S3 IAM最小権限・監査/削除ログ保管期間は、別の小さな設計・Migration PRでレビューする。

## 5. 非破壊テストと受け入れ条件

| 分類 | テスト | 期待結果 |
| --- | --- | --- |
| 期間境界 | 90日直前/到達/超過、365日直前/到達/超過 | 削除候補の計算が一貫し、S3実削除済みと推定を混同しない |
| 日付 | UTC/JST境界、うるう年、添付コピーの遅延 | 最終対話日時とS3作成日時を別々に評価できる |
| 業務状態 | New/Read/Replied/Archived/Spam、メモのみ更新 | Newの例外監査、対話日時の誤延長がない |
| 添付 | なし/1件/複数、S3実体あり/欠損/障害 | 欠損404、障害503、認証前S3アクセスなし |
| 削除 | DB失敗/S3失敗/片方のみ成功/再実行/並列実行 | 未完了を完了と誤認せず、同じ対象を安全に再試行 |
| 孤立 | token発行後の送信未完了、期限切れ、別レコード参照 | 猶予期間と帰属を確認し、誤削除を防ぐ |
| 情報保護 | Secret、顧客本文、ファイル名、S3キーを含むエラー | CI/Issue/監視の出力に機密・個人情報が出ない |
| インフラ | 実S3 Lifecycle、DB権限、バックアップ、復元 | read-onlyで現状を確認。変更は別途承認 |

**リリース前ゲート**：運用方針・例外保全・バックアップ/復元・監査ログの承認→隔離PreviewのダミーデータでMigration/rollbackと統合試験→dry-run件数の人手レビュー→限定件数の手動適用と監視を経て、定期削除の再設計を別途審議する。本番の既存レコード/S3を許可なく削除しない。
